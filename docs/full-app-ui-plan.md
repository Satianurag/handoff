# Handoff — complete web-app execution plan

Final planning specification · 20 September 2026 · implementation has not started in this planning task.

This is the entry document for the next builder. It replaces conflicting UI, mobile/PWA, framework, navigation, and interaction proposals in `execution-brief.md` and the supplied research memo. Those documents are background, not authorization. Preserve the implemented backend contracts except for the explicit additions and corrections below. Do not rebuild authentication, change the chosen runtime model, or deploy as a side effect of reading this plan. The user will separately authorize the complete UI implementation.

**Decision: keep Handoff, but build the handover product, not a generic care dashboard.** The current app is not competitive as a finished submission. The direction becomes credible when two people can review a change, transfer selected responsibilities, see exactly what was accepted, and recover when information changes. This plan locks that experience. Actual household adoption and an overall win remain unproven. Runtime OpenAI use, provider capacity, and public release are still separate release gaps; a complete UI cannot conceal them.

## 1. Product and scope decisions

Handoff serves two to six adults coordinating everyday care for one adult relative. A person may join several households. The recurring job is: **“I’m taking over. What changed, what needs doing, and what am I accepting?”** The outgoing person needs to know what stayed theirs. A solo user can start with a useful task list; shared acceptance is the reason to invite a second person.

The return loop is Today → do or review an item → prepare handover → named recipient reviews and accepts selected work → both people see the receipt → later information is marked as later information. Visits, email, and web sources support this loop. They are not separate mini-products.

Must ship together:

- Real email-code access, household creation/switching, invitation acceptance, and session recovery.
- Today, a complete work list, an agenda, explicit coverage, responsibilities and recurrence, visits and independent ride tasks.
- Handover drafts, publication, partial acceptance, refresh/supersession, decline/cancel, immutable receipts, and recovery of saved drafts.
- Evidence review with current/ proposed values, quotes and provenance; confirmed information never changes merely because a model generated a suggestion.
- Household inbox, conversation matching, reviewed outgoing questions, delivery/reply status, contact controls, quarantine, archive/resolve/delete, and recoverable drafts.
- Activity, personal notifications, people management, owner transfer, former-member responsibility recovery, settings, export and deletion receipts.
- Consistent loading/empty/error/conflict/disconnected states, accessible controls, real data, and full-screen visual verification.
- A separate, clearly labeled synthetic judge session using the same screens and real backend operations. Its integration failures must be visible.

Cut completely: native apps, PWA installation/service workers, mobile-specific navigation redesign, push/SMS, medication or dose tracking, medical advice, symptom journals, general chat, attachments/OCR, EHR import, facility discovery, embedded maps/GPS, calendar grid/sync, billing, analytics dashboards, agent trace screens, presence avatars, command palette/global search, theme editor/dark mode, and social features. Do not leave disabled “coming soon” navigation for any cut feature. External Apple Maps directions and `tel:` links are sufficient for visits. Google Cloud remains limited to model inference and its authentication.

**Useful additions are completion features:** saved handover/draft lists; assignment requests; explicit stale review; sender-versus-office distinction in forwarded mail; source freshness; deletion progress after access is revoked; recovery of work owned by former members. No speculative feature expansion is needed.

## 3. Information architecture and layout

Permanent primary navigation: **Today · Plan · Inbox · History**. Bottom utility links: **People · Settings · Help**. Household switcher at the top; account menu at the bottom; notification bell in the page header. “Plan” contains **Agenda / All work / Handovers**, with a Recurring link under All work. This makes drafts and undated responsibilities discoverable without adding seven primary destinations.

The header includes the household nickname, actual local date/timezone where relevant, and one primary action. Today uses **Prepare handover**; secondary **Add** opens Responsibility / Coverage / Visit. Inbox uses **New question**. No search-shaped decoration without a working search function.

Canonical household prefix: `/h/:householdId`. Item routes validate membership and the item's household; guessing an ID never reveals existence or content. Task, visit and coverage details opened from a list render in a right panel at the canonical URL with the background list retained in memory. Opening those links directly renders a full-width detail page within the shell. Inbox conversation links retain the inbox’s list/detail split, including direct links and reloads; both panes have independent reading positions. Browser Back returns to the exact filter and scroll position. Do not put care text, recipient emails, draft bodies or source quotes in query parameters/history state.

**1920×1080 layout contract:** 248px sidebar, 1px divider; remaining workspace has 48px outer gutters, a 72px header and a centered maximum content width of 1328px. Today has an approximately 840px main column, a 24px gutter and a flexible remaining context column. Lists use available width without stretching text across the whole monitor. Reading pages cap text at 720–800px. Detail panel width is 560px; large edit dialog 640px; short confirmation 440px. These are explicit design choices, not measured claims about Craft.

Today order: pending handover for the viewer → coverage status → due/overdue tasks and assignment requests → changes since their last acceptance. The right column holds next visit and waiting questions. When there is no incoming handover, tasks occupy the top. A quiet state uses short inline explanations, not tall empty cards. Pending proposals remain visible, but opening Today is not a forced review wizard.

Keep the desktop web app usable if its window narrows: columns stack, panels occupy the available width, navigation collapses behind a labeled button, controls wrap. This is ordinary browser resilience, not a mobile-app workstream. The visual reference and approval baseline stays 1920×1080. No device-specific artwork or layout extrapolation from partial screenshots.

## 4. Shared design system and interaction contract

Use existing `web/tokens.css` as the single token source. Existing stack is HTML, CSS and native ES modules with the official Convex browser SDK. **No React/Next.js/shadcn migration.** Component system: shared Handoff renderers/controllers built once on native `<button>`, `<input>`, `<select>`, `<textarea>`, `<details>`, `<dialog>` and ordinary links. Use a single set of locally stored Lucide SVG paths or the existing consistent stroke icons; never mix emoji, filled and outline icon families. No runtime icon CDN. The builder should write domain screens from shared primitives, not restyle controls on each page.

| Token | Locked rule |
|---|---|
| Type | Local Inter for controls/body; quoted `"Source Serif 4"` for wordmark/page title only. Wordmark stays typographic; no new pictorial logo. |
| Sizes | Body 16/24px; metadata 14/20px; labels 14/20px medium; section headings 18/26px semibold; app page title 36/42px serif. Auth may keep its existing larger heading. Do not use all-caps tracked text for ordinary instructions. |
| Colors | Existing ink `#171916`, muted `#656460`, page `#faf8f6`, white surfaces, line `#dedfd9`, blue `#afc3f5`, green `#8bd39e`, yellow `#ffe884`, focus `#21689e`, danger `#a53333`, danger background `#fff1ef`, success `#285f3e`. Add semantic aliases, not near-duplicate hex values. |
| Meaning | Dark filled primary button with white text; blue selected/review emphasis; green confirmed/complete; yellow pending attention; red failures/destructive actions. Every status has text/icon too. Pastel fills take dark text. |
| Borders | Quiet surface dividers may use `--line`; interactive field boundaries need a darker token that passes 3:1 against the adjacent fill, e.g. `--control-border: #8c8d87`, verified before adoption. |
| Shape/spacing | 4px base scale: 4/8/12/16/24/32/48. Controls 10–12px radius, cards/dialogs 16–20px; retain the larger auth card radius only there. Minimum primary control height 44px; list rows at least 64px including metadata. |
| Depth | Flat app surfaces; one subtle shadow for overlays. No marketing-style floating cards on every section. |
| Motion | 120–180ms opacity and at most 4px translation; no spring/bounce or auto-scrolling. Honor reduced motion. New items do not rearrange the focused row. |

Required shared primitives: AppShell, PageHeader, ListRow, StatusBadge, AvatarInitials, SourceQuote, Field/ErrorSummary, SegmentedLinks, EmptyState, Skeleton, InlineNotice, DetailPanel, ConfirmDialog, JobStatus, CursorPager, Toast/LiveRegion. Renderers take escaped text, validated URLs and event callbacks; source/email content never enters executable HTML.

All screens inherit the following **mandatory state contract**; screen specifications add domain states rather than repeating this table:

| State | Required behavior |
|---|---|
| Initial load | Layout-matched skeleton; mark busy; never flash an empty state before a query resolves. |
| Ready/empty/no match | Display actual rows, a contextual add action, or a precise explanation. A filtered empty view offers Clear filter. Zero records does not mean safe, covered or complete. |
| Mutation pending | Disable that action, preserve form input, show its verb (“Saving…”, “Accepting…”). No premature ownership/send/acceptance success. |
| Success | Update from acknowledged server state, keep focus, announce briefly. Navigate only when creating an object or completing a flow. |
| Validation | Labels and linked field errors; focus first invalid field on submit. Keep input and explain correction. No toast-only errors. |
| Conflict | Preserve local edits in memory; show current version and actor when known; offer Reload current values or return to review. Never automatically overwrite/reapprove. |
| Query/service error | Localize failure to its panel. Distinguish invalid arguments/access from transient transport errors. Retrying the same deterministic failing Convex query is not a repair. Provider retries call the specific existing retry action. |
| Disconnected | Keep only in-memory last data with “Connection lost — information may be out of date.” Disable new consequential writes. An already submitted operation may finish; reconnect and reconcile before retry. No custom offline queue or local private database. |
| Expired/revoked | Remove household DOM, subscriptions and cached private state. Session expiry returns to sign-in with a safe internal destination; revocation offers other households. Deletion requester keeps access only to their receipt page. |
| Dirty navigation | Save/discard/stay choice where changes are unsaved; avoid blocking navigation after a successful save. Automatic query updates must not replace an active text input. |
| Missing/retired | Human-readable unavailable state, contextual Back link; never dump IDs or raw server exceptions. Historical records can remain after original evidence expires, labeled accordingly. |

Accessibility: visible focus, skip link, semantic landmarks/headings, real labels, keyboard access without hover/drag, modal Escape/return focus, route title and focus management, and 200% zoom reflow. Target WCAG 2.2 AA contrast (4.5:1 ordinary text; 3:1 qualifying large text and required UI boundaries). This is a design/verification target, not a certification. [Contrast guidance](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).

## 8. Frontend architecture, realtime and storage
